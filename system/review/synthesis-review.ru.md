# Aveli — итоговая системная проверка

## Результат

**Системная аналитическая базовая версия: стабильна**

Документация Aveli образует единую согласованную структуру:

```text
business/
database/
backend/
frontend/
integrations/
system/
```

## Итоги проверки согласованности

### Структура

- старая нумерованная структура удалена после проверки и переноса уникальных знаний;
- корневая навигация отражает текущую системную модель;
- сценарии отказов и готовность к релизу сохранены в `system/review/`;
- отдельная перспектива `operations/` текущему объёму системы не требуется.

### Владение технологиями

Итоговое каноническое размещение:

```text
database/stack/
→ SQLite
→ PostgreSQL

frontend/stack/
→ Flutter / Riverpod / go_router / Drift / клиентские технологии

backend/stack/
→ NestJS / REST / JWT / Argon2id / Prisma

integrations/
→ внешние провайдеры и возможности устройства
```

### Согласованность бизнеса и реализации

Согласованы:

- локальное владение профессиональным рабочим пространством;
- серверное управление идентичностью и доступом;
- пробный период, принадлежащий аккаунту;
- единый доступ ко всему рабочему пространству;
- сохранение рабочего пространства при выходе;
- разрушительная локальная очистка только при явном удалении профиля;
- обязательная серверная сверка после покупки;
- вебхук RevenueCat как источник данных для сверки, а не прямое правило доступа;
- одна агрегированная запись об оплате на одну запись клиента;
- правила архивации/удаления клиента и сохранения исторической услуги;
- текущая модель рабочего расписания и конфликтов записей.

### Трассируемость

Все текущие функциональные области имеют путь от бизнес-правила или требования через критерий приёмки к техническому владельцу на уровне действующего продуктового контракта.

### Известные ограничения

Оставшиеся вопросы не являются скрытыми противоречиями.

Они явно классифицированы в [`open-questions.ru.md`](open-questions.ru.md) как:

```text
принятое ограничение
внешнее подтверждение для релиза
будущее продуктовое решение
будущая измеримая калибровка
триггер изменения архитектуры
```

## Итоговый принцип

Репозиторий считается стабильным, когда неизвестный факт либо разрешён, либо явно классифицирован — а не когда для полноты придуманы ответы на все возможные будущие вопросы.
