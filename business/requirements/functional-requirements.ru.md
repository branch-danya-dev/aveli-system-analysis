> Определяет наблюдаемые возможности и поведение, которые Aveli должен предоставлять в рамках текущего product scope.

---

## Обзор

Функциональные требования описывают **что система должна позволять делать пользователю или самому продукту**.

Они фиксируют ожидаемое поведение, не задавая техническую реализацию.

Пример:

```text
Пользователь должен иметь возможность восстановить существующую подписку.
```

Это относится к `business/requirements/`.

Детали реализации относятся к техническим областям:

```text
backend/
frontend/
database/
integrations/
```

## Аккаунт и аутентификация

| ID | Требование |
|---|---|
| FR-001 | Система должна позволять новому пользователю создать аккаунт. |
| FR-002 | Система должна позволять существующему пользователю войти в аккаунт. |
| FR-003 | Система должна восстанавливать аутентифицированную пользовательскую сессию, если текущей сессии все еще можно доверять. |
| FR-004 | Система должна позволять пользователю выйти из аккаунта. |
| FR-005 | Активный аутентифицированный пользователь должен определять, какое профессиональное рабочее пространство открывается. |

Связанные бизнес-правила:

`BR-023`, `BR-043`–`BR-047`

## Trial и Access

| ID | Требование |
|---|---|
| FR-006 | Новый аккаунт должен получать пробный период длительностью 30 дней. |
| FR-007 | Один и тот же аккаунт должен сохранять исходное состояние trial после logout, переустановки приложения и сброса локального рабочего пространства. |
| FR-008 | Система должна определять, может ли текущий аутентифицированный пользователь открыть рабочее пространство. |
| FR-009 | Доступ может предоставляться через lifetime access, manual access, active subscription или active trial. |
| FR-010 | Система должна предотвращать вход в рабочее пространство, если действующего источника доступа нет. |
| FR-011 | Доступ должен применяться ко всему рабочему пространству целиком, а не через независимые feature-level paywall. |
| FR-012 | Истечение доступа не должно удалять существующую информацию профессионального рабочего пространства. |
| FR-013 | Восстановление действующего доступа должно снова делать существующее рабочее пространство доступным. |

Связанные бизнес-правила:

`BR-001`–`BR-013`, `BR-025`, `BR-026`

## Границы функциональных требований

Функциональные требования определяют ожидаемое поведение.

Они не должны содержать implementation decisions:

```text
Use PostgreSQL
Use SQLite
Use JWT
Use RevenueCat SDK
Use REST
Use Docker
```

Если такое решение необходимо, оно должно находиться в соответствующей технической документации или ADR.

Функциональное требование может ссылаться на техническую область, если реализация требует дополнительной детализации.

## Открытые области правил

Некоторые сценарии намеренно оставлены на высоком уровне до финализации подробных бизнес-правил.

К ним относятся:

- точные правила конфликтов записей;
- точные правила delete/archive клиента;
- точные правила delete/deactivate услуги;
- точный lifecycle оплаты;
- точное merge-поведение при export/import;
- точная длительность offline verification.

После фиксации этих правил они должны быть описаны в `business-rules` и отражены в соответствующих functional requirements без добавления технических деталей.
